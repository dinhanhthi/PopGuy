# Releasing PopGuy (Sparkle auto-update runbook)

This is the manual checklist for cutting a signed, notarized PopGuy release that
the in-app Sparkle updater can deliver to existing users.

> **Releases are built locally only — there is no CI release workflow.** After the
> one-time setup (§0), a release is: bump + changelog (§1, §3), commit + push, then
> `scripts/ship.sh`, which chains `build-and-notarize.sh` (§2) → `publish-release.sh`
> (§4) → `publish-appcast.sh` (§5). `/cf-ship` drives this end to end. §2–§5 below
> explain what each script does. On a new machine only §0 needs redoing (restore the
> Developer ID cert, the `popguy-notary` profile and the Sparkle private key).

PopGuy uses **Sparkle 2.x** (added via Swift Package Manager). Sparkle does **not**
read the GitHub API — it polls a hosted `appcast.xml` feed. GitHub Releases host the
signed `.zip`; the appcast (generated by Sparkle's `generate_appcast`) is hosted at a
stable URL and lists each build with an EdDSA signature.


| Fact                                          | Value                                                                             |
| --------------------------------------------- | --------------------------------------------------------------------------------- |
| Repo                                          | `https://github.com/dinhanhthi/PopGuy`                                            |
| Apple Team ID                                 | `86H6CNLN4C`                                                                      |
| Feed URL (`SUFeedURL` in `PopGuy/Info.plist`) | `https://dinhanhthi.github.io/PopGuy/appcast.xml`                                 |
| Sparkle compare key                           | `CFBundleVersion` (= `CURRENT_PROJECT_VERSION`) — **must increase every release** |
| Marketing version                             | `CFBundleShortVersionString` (= `MARKETING_VERSION`) — user-facing                |


> Sparkle compares `**CFBundleVersion`**, not the marketing version. If you forget to
> bump it, **no update is ever detected.** Bump it for every single release.

## 0. One-time setup (do once per machine / project)

> **You just enrolled in the Apple Developer Program.** Work through §0.0 → §0.4 once,
> in order. §0.0–§0.1 switch you from the old free/personal-team signing to the paid
> Developer ID; §0.2 wires Sparkle; §0.4 removes the leftover self-signed "fake" cert.

### 0.0 Confirm your paid Team ID (do this first)

This runbook and all 8 build configs in `project.pbxproj` are wired to team
`**86H6CNLN4C`**. Before anything else, confirm that is your **paid** Team ID:

1. Sign in at [https://developer.apple.com/account](https://developer.apple.com/account) → **Membership details**.
2. Read **Team ID**. It must be `86H6CNLN4C`.

> Your Keychain currently holds an `Apple Development` cert for team `**SAM5K74884`** —
> that is your old **free/personal** team, not the paid one. Everything below replaces
> it with paid-team certs. If your Membership Team ID is **not** `86H6CNLN4C`, stop and
> update `DEVELOPMENT_TEAM` in `project.pbxproj` (all 8 occurrences), the `teamID` in
> `ExportOptions.plist` (§2), the `--team-id` in §0.1 step 6, and the table at the top
> of this file — then continue.

### 0.1 Apple-issued signing identities (REQUIRED — hard prerequisite)

You now need **two** real Apple certs, both under the paid team `86H6CNLN4C`:

- `**Apple Development`** — signs **Debug** builds you run from Xcode. The project must
keep signing Debug with a **Team-bearing** Apple Development cert; an ad-hoc or
no-team cert breaks the Keychain partition list and causes an infinite password
prompt. Your existing one is under the *personal* team `SAM5K74884`; regenerate it
under the paid team.
- `**Developer ID Application`** — signs the **Release** build you distribute. This cert
**requires the paid program** (free teams can't create it). macOS Gatekeeper
**silently blocks** a Sparkle-installed update signed with anything else — it fails at
*install* time, not build time, so you won't see an error until a user's update
silently fails.

1. **Regenerate the Apple Development cert under the paid team (for Debug).**
  Xcode → Settings → Accounts → your Apple ID. If the paid team isn't listed, click
   the team dropdown / **Download Manual Profiles** so Xcode picks up the new
   membership. Then **Manage Certificates…** → `+` → **Apple Development** while the
   paid team is selected. Build & run Debug once and confirm no repeating Keychain
   password prompt (that symptom means Debug is signing with a non-paid-team cert).
2. **Create the Developer ID Application cert (for Release).**
  Same **Manage Certificates…** sheet → `+` → **Developer ID Application**. (Or create
   it in the Apple Developer portal → Certificates → `+` → *Developer ID Application*.)
   Verify it landed in the Keychain:
3. The Release config already has `**ENABLE_HARDENED_RUNTIME = YES`** — required for
  notarization. Keep it.
4. Signing is already wired up: the **PopGuy app → Release** config signs with
  `CODE_SIGN_IDENTITY = "Developer ID Application"` and `CODE_SIGN_STYLE = Manual`
   (team `86H6CNLN4C`, no provisioning profile — Developer ID doesn't use one). So
   Release archives are Developer-ID-signed directly; **nothing to change here.**
   Debug stays `Apple Development` / `Automatic`, so daily `Run`-from-Xcode is
   unaffected. The §2 export still uses `ExportOptions.plist` (`method=developer-id`) —
   it agrees with the project setting and `-exportArchive` requires an options plist
   regardless. Note: manual signing means a Release build on a machine **without** the
   Developer ID cert will fail to sign — expected; only the release machine builds
   Release.
5. **Test PopGuy's core capture paths under the signed + hardened build early** —
  the hardened runtime can interfere with them unexpectedly; do not leave this to
   the end. Under a Developer-ID-signed, hardened build confirm:
  - `CGEventTap` hotkey install still works (needs Accessibility trust at runtime).
  - Synthetic paste-back (Cmd+V via `CGEvent`) still works.
  - Accessibility text capture (`AXUIElement`) still works.
   If any break, resolve the entitlement / hardened-runtime interaction before
   continuing — a release that captures nothing is worse than no release.
6. Store a notarization credential profile in Keychain once:
  ```sh
   xcrun notarytool store-credentials "popguy-notary" \
     --apple-id "<your-apple-id-email>" \
     --team-id 86H6CNLN4C \
     --password "<app-specific-password>"   # appleid.apple.com → App-Specific Passwords
  ```

### 0.2 Sparkle EdDSA signing keys (REQUIRED — hard prerequisite)

Sparkle verifies every downloaded update against an EdDSA (ed25519) **public** key
baked into the app's `Info.plist` (`SUPublicEDKey`). The matching **private** key
signs each release and must **never** be committed.

The `generate_keys` / `generate_appcast` tools ship inside the Sparkle SPM artifact.
After a build, find them under:

```
~/Library/Developer/Xcode/DerivedData/PopGuy-*/SourcePackages/artifacts/sparkle/Sparkle/bin/
```

(Or download the Sparkle release tarball from [https://github.com/sparkle-project/Sparkle/releases](https://github.com/sparkle-project/Sparkle/releases) and use its `bin/`.)

Generate the keypair once:

```sh
./bin/generate_keys
```

- It stores the **private** key in your **login Keychain** (never on disk, never in git).
- It prints the **public** key. Copy it into `PopGuy/Info.plist`, replacing the
placeholder `REPLACE_WITH_generate_keys_OUTPUT` (and delete the `TODO` comment above it).

> **Until the real public key replaces the placeholder, the updater is inert** — that
> is expected, not a bug. A malformed `SUPublicEDKey` makes Sparkle **fail closed**
> (signature validation cannot pass), so no unsigned/forged binary can install. Verify
> this safe-fail behavior the first time you wire up a real feed.

**Back up the private key.** It lives in your login Keychain, but Sparkle's EdDSA key
is *not* a code-signing certificate — do **not** try to export it as a `.p12` (that
format is for the Developer ID cert, §0.1). Use Sparkle's own export instead:

```sh
./bin/generate_keys -x sparkle_private_key.txt   # writes the private key to a file
```

Store `sparkle_private_key.txt` in a secret store (password manager), then **delete it
from disk** and never commit it. To restore on another machine: `generate_keys -f sparkle_private_key.txt`. The file's contents are as sensitive as the Keychain key —
anyone holding it can sign updates your users will accept.

> If you lose the private key you can never ship a Sparkle update that existing users
> will accept without re-keying via a manually-installed build.

### 0.3 Account hardening (defense-in-depth)

The whole update chain trusts one GitHub account (feed host + release assets). Enable
**2FA** on it. Optionally mirror the appcast on a second independent host. Signature
verification is the real integrity boundary, but account compromise still controls
distribution.

### 0.4 Remove the self-signed "fake" certificate

Before the paid program, builds were shared via a **self-signed** `PopGuy Self Sign`
cert (the `scripts/sign-and-share.sh` dev path — see
`[DEV_DISTRIBUTION.md](DEV_DISTRIBUTION.md)`). With a real Developer ID that path is
**superseded** for any distribution; remove the leftover cert so nothing accidentally
signs against it.

1. Check whether it is even on this machine:
  ```sh
   security find-identity -v | grep "PopGuy Self Sign"
  ```
   If it prints nothing, there is nothing to remove here — it may live on another build
   machine, or was already deleted. Skip the rest.
2. If it *is* listed, delete the identity (cert **and** its private key). Easiest in
  **Keychain Access** → search `PopGuy Self Sign` → delete both the certificate and the
   matching private key. Or by hash from the `find-identity` output:
3. Confirm it is gone:
  ```sh
   security find-identity -v -p codesigning   # should show only your real Apple certs
  ```

> The dev files (`scripts/sign-and-share.sh`, `scripts/dev-entitlements.plist`,
> `DEV_DISTRIBUTION.md`) are left in place but are now dead for distribution — removing
> the cert disables that path. The official release uses **only** the Developer ID +
> notarization flow below. Do **not** reuse `dev-entitlements.plist` (its
> `disable-library-validation` exists solely because a self-signed cert has no Team ID;
> the Developer ID build shares a real Team ID and must keep library validation on).

## 1. Bump the version (every release)

From the repo root, use the helper script:

```sh
scripts/bump-version.sh 1.1.0     # set marketing version 1.1.0, build number +1
scripts/bump-version.sh           # keep marketing version, build number +1 only
```

It edits `MARKETING_VERSION` (CFBundleShortVersionString) and increments
`CURRENT_PROJECT_VERSION` (CFBundleVersion) directly in `project.pbxproj`, prints
the change, and leaves the working tree for you to review. All targets (app + test
bundles) are set to the same numbers — test-bundle versions are cosmetic.

> Not `agvtool`: this project has no `VERSIONING_SYSTEM = apple-generic`, so
> `agvtool` misreads the versions. The script edits the pbxproj directly instead.

Confirm and commit the bump:

```sh
git diff PopGuy.xcodeproj/project.pbxproj
```

## 2. Build, sign, notarize, export

> **Use `scripts/build-and-notarize.sh`.** The manual steps below are for reference only:
> `xcodebuild -exportArchive` is **broken** for PopGuy on Xcode 26 and 27 ("expected one {}
> but found developer-id") because of the embedded MLX helper. The script instead copies
> the Developer-ID-signed app out of the archive with `ditto`, re-signs Sparkle's 4 nested
> helpers inside-out, then notarizes and staples both the zip and the DMG.

Archive the Release build:

```sh
xcodebuild -project PopGuy.xcodeproj -scheme PopGuy -configuration Release \
  -archivePath build/PopGuy.xcarchive archive
```

Export a Developer-ID-signed `.app`. Create `ExportOptions.plist` once (repo root, not
committed) — minimal contents:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>method</key>            <string>developer-id</string>
    <key>signingStyle</key>      <string>manual</string>
    <key>teamID</key>            <string>86H6CNLN4C</string>
</dict>
</plist>
```

Then export:

```sh
xcodebuild -exportArchive -archivePath build/PopGuy.xcarchive \
  -exportOptionsPlist ExportOptions.plist -exportPath build/export
```

Zip it (Sparkle distributes a zipped app bundle; `--keepParent` keeps `PopGuy.app`).
This **first zip is a throwaway** — it exists only so `notarytool submit` has something
to upload; it is NOT the file you ship (it lacks the stapled ticket):

```sh
cd build/export
ditto -c -k --keepParent PopGuy.app PopGuy-1.1.0.zip
```

Notarize, staple the ticket onto the `.app` (you staple the **bundle**, not the zip),
then **re-zip the stapled app** — this re-zipped file is the one you publish:

```sh
xcrun notarytool submit PopGuy-1.1.0.zip --keychain-profile "popguy-notary" --wait
xcrun stapler staple PopGuy.app
ditto -c -k --keepParent PopGuy.app PopGuy-1.1.0.zip   # overwrite throwaway with the stapled build
```

Verify before publishing:

```sh
spctl -a -vv -t exec PopGuy.app    # should report: accepted, source=Notarized Developer ID
```

> **DMG for manual download.** The `.zip` above is what Sparkle auto-update consumes,
> but it is fragile for first-time human installs: a third-party unarchiver pollutes
> `Sparkle.framework`'s root with `._*` files, breaking the code seal → Gatekeeper shows
> a malware warning. `scripts/build-and-notarize.sh` therefore also
> builds a **notarized DMG** (drag-to-install, no extraction) and uploads it alongside
> the zip. To produce one manually from the **stapled** app:
>
> ```sh
> cd build/export
> mkdir dmg-stage && cp -R PopGuy.app dmg-stage/ && ln -s /Applications dmg-stage/Applications
> hdiutil create -volname "PopGuy" -srcfolder dmg-stage -ov -format UDZO PopGuy-1.1.0.dmg
> codesign --force --timestamp --sign "Developer ID Application" PopGuy-1.1.0.dmg
> xcrun notarytool submit PopGuy-1.1.0.dmg --keychain-profile "popguy-notary" --wait
> xcrun stapler staple PopGuy-1.1.0.dmg
> spctl -a -t open --context context:primary-signature -v PopGuy-1.1.0.dmg   # accepted
> ```

## 3. Write the changelog entry

`CHANGELOG.md` (repo root, tracked) is the **single source of truth**
for release notes: the same
section feeds both the GitHub release body and the Sparkle appcast notes. Add a section
for this version in [Keep a Changelog](https://keepachangelog.com/) format:

```markdown
## [1.1.0] - 2026-06-22

### Added
- …
### Changed
- …
### Fixed
- …
```

> The header version **must match `MARKETING_VERSION` exactly** (the value
> `bump-version.sh` set in §1). `publish-release.sh` derives the version from the
> project and extracts `## [<that version>]`; if the header doesn't match (e.g. project
> is `1.1.0` but the header says `1.1`), it fails. Use the same number in both.

Commit the changelog (you commit; the script never does).

## 4. Tag + publish the GitHub Release

One script derives the version from the project, extracts the matching changelog
section, tags, and publishes — so the tag, the app version, and the release notes can
never drift:

```sh
scripts/publish-release.sh build/export/PopGuy-1.1.0.zip
```

Run it from `**main**` — the script refuses to run on any other branch (releases must
be tagged from `main`; merge your release commit there first).

It:

- derives `VERSION` from `MARKETING_VERSION` → `TAG=vVERSION` (tag always == app version),
- checks you are on `main`, the zip filename contains `VERSION`, `gh` is authenticated,
and the tag does not already exist (local + origin),
- extracts the `## [VERSION]` section from `CHANGELOG.md` (repo root; fails if missing/empty),
- writes it to `PopGuy-VERSION.md` next to the zip — the notes file `generate_appcast`
embeds into the appcast in §5,
- after a `[y/N]` confirm, creates + pushes the annotated tag and runs
`gh release create vVERSION <zip> --title "PopGuy VERSION" --notes-file …`.

If `gh release create` fails *after* the tag was pushed, the script prints how to undo
the tag (`git push origin :refs/tags/vVERSION && git tag -d vVERSION`) so you can re-run.

## 5. Generate & publish the appcast feed

The feed lives at the repo root as `**appcast.xml*`* (tracked on `main`). It is published
to the `SUFeedURL` `https://dinhanhthi.github.io/PopGuy/appcast.xml` by
`.github/workflows/deploy-appcast.yml`, which copies **only** `appcast.xml` into the Pages
artifact — `docs/` and source are never published.

> **One-time:** GitHub repo → **Settings → Pages → Source = "GitHub Actions"**. Without
> this the deploy workflow's `deploy-pages` step fails. The placeholder `appcast.xml` +
> workflow are already committed, so the first push to `main` after enabling this goes live.

Regenerate the feed. The release asset and its `PopGuy-1.1.0.md` notes file now exist
(from §4). Put every release `.zip` you want listed into one folder (e.g.
`build/appcast-archives/`), each alongside its `PopGuy-<version>.md` notes file, then:

```sh
./bin/generate_appcast build/appcast-archives/ \
  --download-url-prefix "https://github.com/dinhanhthi/PopGuy/releases/download/v1.1.0/"
cp build/appcast-archives/appcast.xml appcast.xml   # bring the feed to the repo root
```

`generate_appcast`:

- signs each archive with the **private** EdDSA key from your Keychain,
- writes/updates `appcast.xml` (with `<enclosure>` `sparkle:edSignature` + length),
- embeds the sibling `PopGuy-<version>.md` as that item's release notes,
- sets each `<enclosure url>` using the `--download-url-prefix` (the GitHub Release asset
base URL from §4, so the feed links to the uploaded `.zip`).

Commit + push the updated root `appcast.xml` on `main` — the workflow redeploys it (it
triggers only on `appcast.xml` changes):

```sh
git add appcast.xml && git commit -m "release: appcast v1.1.0" && git push
```

Confirm it is live (give Pages a minute):

```sh
curl -fsSL https://dinhanhthi.github.io/PopGuy/appcast.xml | head
```

## 6. Verify the end-to-end update path

1. Install the **previous** released build (one with a lower `CFBundleVersion`).
2. Launch it. With automatic checks on (default via `SUEnableAutomaticChecks`), Sparkle
  does a background check and the gentle-reminder delegate lights up:
  - the **menubar status-icon badge** (accent dot), and
  - the **Settings banner** ("Version 1.1.0 is available").
3. Click **Update now** (banner) or **Update to v1.1.0…** (menu) → Sparkle's standard
  install flow runs. Confirm the app downloads, signature-verifies, installs, and
   relaunches at the new version.
4. Also confirm **Settings → Check for Updates** works on demand, and the
  **Automatically check for updates** toggle persists across relaunch.
